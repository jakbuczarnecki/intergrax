# PLAN T-IGX-044-F (amendment 5) - EQO-A remediation node PT-E05 (T-ENF-5): IIAC validator hardening on the material governance paths

Scope statement: this plan edits five of the six `MATERIAL_GOVERNANCE_PATHS`, edits one existing test (the PT-E04 scope guard, which asserts the opposite of the wiring), edits the module docstring of one PT-E04 file that becomes material, and adds one test file. It changes what the IIAC validators and the activation gate accept for NEW (v2) manifests and for NEW activation records, wires the PT-E04 verifiers into the activation gate, makes the gate refuse a v2 manifest that is not final, and claims no PASS, closure, FRZ promotion or independent verification. Approval state is recorded only in the ticket's Approved section and lifecycle state.

## 1. Purpose

EQO-A Campaign A found that IIAC independence rests on string comparison and role labels (A2-038), that three published manifests fail the repository's own validator while staying tolerated (A2-006, handled in PT-E04 without touching their bytes), and that a delegated operator line is only a format check (A2-038 operator line). Plan B of the WP-7 enforcement plan (`WP-7/PLAN.md` V1, V2, V3; ticket row T-ENF-5; decisions DP-58 and DP-68) specifies the hardening of the validators themselves. PT-E04 (T-IGX-044-E, merged as PR #623, `a8b325c06d60b01ab88b7d3e61bb4763095eb3d8`) added the corpus, artifact and delegation verifiers as new, unwired files and left the wiring and the strictness of the existing validators to this ticket.

Design rule that follows from the Operator decision (a) of 2026-11-17 (addendum 3 of `OPERATOR_ANSWERS_CODE_WAVE_TRANSCRIPTION.md`): every new strictness applies to NEW manifests (marked v2) and to NEW activation records only. A manifest without the v2 marker is a v1 manifest and keeps exactly today's verdict. Measured at `origin/development` `2727a2c2364a97492202b931375772a400279a9b`: 41 manifest files, none carries any schema or state marker today, 38 validate and 3 (the known drafts) do not; 20 of the 41 contain a placeholder-like token in an identity field (regex `HISTORICAL_UNRECORDED|PENDING|TBD|UNKNOWN|TODO`, deliberately broad), so placeholder rejection cannot apply to v1.

### 2a. Inversion of the PT-E04 scope guard

What the old guard protected: the PT-E04 promise that its files lie outside the IIAC trust boundary (editing them could not stale the audit through ACT-N11, and nothing they do could change a gate verdict). The guard at `tests/unit/governance/test_iiac_new_verifiers.py:333-346` has three assertions: (1) no PT-E04 file is in `MATERIAL_GOVERNANCE_PATHS`; (2) no material `.py` file contains a PT-E04 module stem; (3) the text of `iiac_activation_gate.py` does not contain `iiac_known_draft_manifests`. The wiring of section 2 makes all three fail: (1) and (2) because the four files become material and the gate names the verifiers; (3) because `MATERIAL_GOVERNANCE_PATHS` is a literal inside the gate, so the new entry `scripts/governance/iiac_known_draft_manifests.v1.json` puts the stem into the gate text whatever arguments the corpus call uses (an earlier draft of this plan wrongly said (3) would still pass).

The renamed test `test_wired_new_files_are_material_and_only_the_gate_names_them` asserts the wired state, each assertion with its state before and after:

1. Material set. Before: none of the PT-E04 paths is a member. After: exactly four PT-E04 paths are members (`iiac_verifier_common.py`, `verify_iiac_manifest_corpus.py`, `verify_iiac_manifest_artifacts.py`, `iiac_known_draft_manifests.v1.json`); `verify_iiac_delegation_refs.py`, the test file and the fixtures are not.
2. Exact sets of names. Before: no material `.py` file names a PT-E04 module stem. After: (a) the set of material `.py` files outside the four PT-E04 members and `iiac_activation_gate.py` that name any PT-E04 module stem (`iiac_verifier_common`, `verify_iiac_manifest_corpus`, `verify_iiac_manifest_artifacts`, `verify_iiac_delegation_refs`) is empty; (b) the set of PT-E04 stems that `iiac_activation_gate.py` names is exactly `{verify_iiac_manifest_corpus, verify_iiac_manifest_artifacts}` (it does not name `iiac_verifier_common` or `verify_iiac_delegation_refs`: the gate runs the two verifiers as subprocesses and imports nothing from PT-E04). The members themselves name each other (the verifiers import `iiac_verifier_common`) and are not constrained.
3. The allowlist path has one spelling. Before: the stem `iiac_known_draft_manifests` is absent from the gate text. After: parsed with `ast`, every string constant of the gate that contains the stem equals `scripts/governance/iiac_known_draft_manifests.v1.json`, and such constants occur only in the `MATERIAL_GOVERNANCE_PATHS` literal and in the one module-level assignment that names the default allowlist path used by the corpus call; no other expression of the gate spells that path. (The gate also reads that file once, to enforce NT-E05-12; this is not constrained by the guard.)

What the inversion keeps: the gate is the only wiring point, and the PT-E04 files that are not wired stay non-material and unreferenced by any material file. What it gains: exact-set checks (a removed wired file or a second wiring point fails the guard; NT-E05-27 checks membership per file). What is lost, by intent: the wired PT-E04 files can no longer be edited without staling the audit, and the gate's verdict now depends on PT-E04 code. Weakening an existing guard in the same pull request that breaks it is a pattern; it is acceptable here only because the three assertions above are exact and falsifiable, and the change is the Operator's decision through Q-E05-08.

## 4. Design

### 4.1 Manifest v2 and strict default (V1)

A manifest is v2 when it carries `manifest_schema_version: "v2"`. v2 adds `manifest_state` (`draft` or `final`), `identity_provenance` and `handoff_record_ref`. A `draft` may carry placeholders and may not be used as certifying (the corpus verifier of PT-E04 already fails a non-final manifest under `--certifying`). A `final` is held to the PT-E04 artifact rules as errors, not warnings: SHAs exist and follow the strict chain (rule for new manifests, Operator decision (a)), the four digests equal the bytes of the files they name, verdict is `PASS` or `PASS_SCOPED`, no placeholder strings. v1 manifests are never reinterpreted.

### 4.2 Identity and provenance (V2)

`identity_provenance` per role: `{issuer, session_uuid, started_at_utc, host_receipt_ref}`, `host_receipt_ref` = `path@sha` of a tracked export of the host session id. Checked: the file exists at the commit, the commit is an ancestor of the audit-execution SHA, the file contains the `session_uuid`, the `session_uuid` equals the role's session id after normalisation, no `session_uuid` or receipt repeats across the three roles, and none repeats in another v2 manifest of the corpus. The check proves consistency of recorded identifiers, not who typed them: independence stays `process_enforced` (open question Q-E05-05 for signed commits).

### 4.3 Countersignature and operator line kinds (V2, V3)

The handoff record named by `handoff_record_ref` must contain a line `Countersigned: operator @ <ts> manifest-digest <sha256>` whose digest equals the sha256 of the canonical JSON of the manifest without its `handoff_record_ref` field (`json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False).encode("utf-8")`, where `obj` is the parsed manifest with its top-level key `handoff_record_ref` removed whatever its value; only the top level is touched, a v2 final manifest without that key is already an error). Further rules: the root must be a JSON object; duplicate object keys at any depth reject the manifest (detected when the audit script parses the file with `object_pairs_hook`, because a parsed manifest has already dropped them); floats and non-finite numbers reject it (only integers, strings, booleans, null, arrays and objects); a UTF-8 BOM is ignored when reading; keys are ordered by code point (the Python default). These rules apply to the digest of a v2 `final` manifest only (`manifest_countersign_digest` raises on a float, a non-finite number or a non-object root; the audit script reports each rule with a stable error text and exits 1); a v1 manifest is read exactly as today, and NT-E05-11 asserts each rule. One normative test vector, written into the protocol document and asserted in NT-E05-11: the manifest `{"a":1,"b":"\u00e9","handoff_record_ref":"p@<40 zeros>"}` canonicalises to the UTF-8 bytes of `{"a":1,"b":"é"}` with sha256 `09ad9fd2fb648cb2f62141215828ea00a62c299db05d20aa9ade2f527a301cc6`. The digest cannot be taken over the manifest bytes: the manifest names the commit of the handoff record that holds the digest, which would be circular; presence and digest are checked mechanically, authorship is not. The operator line of an activation record is `personal` (`Approved IIAC policy activation <version>: operator @ <ts>`) or `delegate` (`operator-delegate @ <ts>` plus a `Delegation: <path>@<sha40>` pointer); the gate resolves the pointer with `resolve_delegation_ref` and fails when the record names another stage, is not an ancestor of HEAD, or names the implementer as the delegate. Open question Q-E05-03 asks whether this resolver stays a small copy in `iiac_common.py` (default) or reuses `ticket_approval.resolve_delegation` (PT-E02).
