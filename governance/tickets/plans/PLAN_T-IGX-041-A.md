## Problem

The B-D1 components (upgrade, retire, rollback, emergency revocation, skill lifecycle) exist and are component-tested, but four defects exist in code that is already composed, and 18 D1-cited suites are red:

1. **Revoked packages can be re-activated or restored by a normal operator action (F-D1-02, HIGH).** `AgentPlatformAdminService.activate_revision` (`admin_service.py:1392`) checks scope, authorization and the LLM profile pin only; `rollback_revision` and `handle_post_cutover_failure` go through `_execute_governed_rollback` (`admin_service.py:2323`) into `ActivationService.rollback`, whose default revalidation hook only checks that a materialization artifact digest exists. Revocation is re-evaluated only at build (`_assert_runtime_revision_trust_admission`, `admin_service.py:1692`) and in the emergency path (`revision_passes_current_trust_admission`). A digest revoked after build can be served again. Reproduced by the auditor (probes P9, P13); the code path was re-read here.
2. **`respond_to_emergency_revocation` is an unauthenticated mutator (F-D1-03, HIGH, authorization part).** It has no principal and neither tenant-scope nor policy authorization (`admin_service.py:1508`), and it accepts a caller-supplied request whose `revocation_state`, `trust_policy` and `evaluated_at` replace the injected trust sources, then performs `ActivationService.rollback`. Every other mutating method of the service has a principal. A grep over the repository finds callers only in three D1-related test files and two audit probes; there is no production caller (see Excluded findings).
3. **No application-ownership guard on install and upgrade (F-D1-05, MEDIUM).** `retire_agent` calls `_assert_installation_application_scope` (`admin_service.py:962`); `install_agent` into an occupied slot and `upgrade_agent` resolve the slot by `(environment_id, slot)` only, so a same-tenant principal acting for another application id upgrades the slot another application bound (probe P1).
4. **Upgrade can leave a VERIFIED candidate and failure paths leave no evidence object (F-D1-06, MEDIUM).** In `upgrade_agent` (`admin_service.py:846-907`) only `mark_verified` and `promote_verified_to_active` are guarded; an exception from `_resolve_package_contracts`, `evaluate_agent_upgrade_admission` or the binding lookup leaves the candidate `VERIFIED` (probe P4), and the `TransitionResult` of `mark_failed_candidate` in the except paths is discarded before the re-raise (probe P5), so the persisted transition has no event anywhere. Success paths return `audit_event_types` strings (`_event_types`) that nothing consumes.
5. **18 D1-owned suites are red at the audited SHA and at the activation pin (F-D1-11, MEDIUM).** Root-caused here (one pytest process per group, logs `.tmp/session/t041a/acp2.log`, `six.log`):

## Deliverables

Pinned regression tests first (each shown failing for the stated reason on unchanged code), then the fixes. New tests go into a new directory `tests/qualification/pdc_x/d1_repair/` so that the existing `tests/qualification/pdc_x/d1/` tests are edited only where a signature changes (Deliverable 3).

1. **Pinned tests (new files in `tests/qualification/pdc_x/d1_repair/`)**, using the same stack builders as the existing D1 tests and the injected revocation-state source (never a real credential, key or network):
   - F-D1-02 positive/negative: after serving rev-2 with prior rev-1, revoking the prior package digest makes `rollback_revision` raise a typed `AgentPackageTrustError` (reason `package_digest_revoked`) and leaves serving unchanged; same for `handle_post_cutover_failure` rollback; `activate_revision` of a built revision whose package digest was revoked after build raises and does not commit; revoked publisher and revoked evidence id are denied the same way; an un-revoked target still rolls back and activates (positive control); a missing installation or trust record for an enabled roster entry of the target is denied (fail closed); denied principals still get the tenant/policy error first (the trust check runs after authorization and does not leak revocation state to a foreign tenant).
   - F-D1-03: `respond_to_emergency_revocation` with a principal of another tenant raises the tenant-authority error and does not roll back; with a DENY mutation boundary it raises the governance error and does not roll back; the revocation state is taken only from the injected source (a caller-supplied snapshot can no longer be passed: the parameter does not exist; a test asserts the signature); a positive control with an allowed principal and a really revoked active package rolls back to a trusted prior revision (the existing service behaviour).
   - F-D1-05: `install_agent` into a slot occupied by another application's installation, and `upgrade_agent` for an application id that has no binding to the slot, raise `AgentDistributionNotFoundError` and change nothing (no candidate row, no authority record); the owning application still upgrades and installs; install into a fresh, unoccupied slot is unchanged.
   - F-D1-06: an exception raised after `mark_verified` (injected failing `_resolve_package_contracts` / admission evaluation / binding lookup) leaves the candidate `FAILED_CANDIDATE`, never `VERIFIED`, and the previous installation `INSTALLED_ACTIVE`; with a recording sink every transition (including the `trust_verification_failed`, `promotion_failed` and new failure paths) reaches the sink as a full `AgentDistributionEvent` carrying `reason_code`; with no sink behaviour and return values are byte-identical to today.
   - F-D1-12 by-product: DENY boundary on `upgrade_agent` and `retire_agent` raises the governance error and leaves the slot untouched (kills M2); an upgrade whose version equals the active version is rejected (kills M7); the rejection `reason_code` is present on the `failed_candidate` event (kills M10). F-D1-14 by-product: registering a second contract with an existing id is rejected.
2. **Fix F-D1-02 in `intergrax/agent_distribution/admin_service.py`.** One private method `_assert_revision_trust_admissible(revision, application_id, application_environment_id)` builds the roster of the target revision with the already injected `EffectiveRosterAuthorityService` (`require_for_revision`, as at `admin_service.py:2096`) and evaluates every enabled entry with the injected `AgentPackageTrustCoordinator.assert_install_admission`, the injected revocation-state source, trust-policy source and evaluation-time source; typed `AgentPackageTrustError` propagates (no new error class). It differs from the build-time check in one respect: for activation and rollback an enabled entry without an installation or without a trust record is a denial (the build path keeps its `continue`; that behaviour is not changed). It is called in `activate_revision` after `_authorize_activation` and before `prepare_candidate`, and inside `_execute_governed_rollback` after `_authorize_rollback` and before `ActivationService.rollback`, which covers `rollback_revision` and `handle_post_cutover_failure`. No change to `activation.py`, `emergency_revocation_response.py` or `package_trust.py`.
3. **Fix F-D1-03 in `admin_service.py`.** New signature `respond_to_emergency_revocation(*, application_id, application_environment_id, principal, expected_current_traffic_revision_id=None, expected_serving_pointer_revision=None)`: `_require_environment_tenant_scope` first; when the serving record has a prior revision, the rollback mutation is authorized with `_authorize_rollback` (same boundary, same evidence as `rollback_revision`) before the one-shot service runs; the request object is always built inside the service from the injected revocation, policy and time sources, so a caller can no longer substitute a snapshot. The scope-mismatch check on the request disappears with the parameter. Callers in `tests/integration/agent_distribution/test_ac6_trust_lifecycle_e2e.py`, `tests/integration/agent_distribution/test_enterprise_projection_rehydration_e2e.py` and `tests/qualification/pdc_x/d1/test_d1_adversarial_lifecycle.py` are updated to the new signature (the implementer re-greps; the audit probes under `iiac_evidence/` are frozen evidence and are not edited). ## Acceptance

- After a digest is revoked, `rollback_revision`, `handle_post_cutover_failure` and `activate_revision` refuse to restore or activate a revision whose enabled packages include it, with a typed error and unchanged serving state; positive controls still pass.
- `respond_to_emergency_revocation` requires a principal with tenant scope and policy authorization and cannot take a caller-supplied revocation snapshot.
- `install_agent` into an occupied slot and `upgrade_agent` enforce the application-ownership check.
- A failed upgrade never leaves a `VERIFIED` candidate; with a sink every install/upgrade/retire transition, including failure paths, is delivered as an event; without a sink behaviour is unchanged.
- The 18 ids of `iiac_evidence/PDC-X/D1/logs/failed_ids.txt` are green (or, for the durable CAS test, root-caused and green per Deliverable 7e) without any skip, xfail or loosened assertion; M2, M7 and M10 are killed by the new tests.
