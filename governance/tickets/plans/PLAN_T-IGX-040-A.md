### Repair 1 — F-49: the single `openai` catalog row resolves the wrong integration for the embedding category

Reproduced on `origin/development` (67b4fc956), cleared catalog, `register_openai_managed_retrieval_integration()` then `register_openai_embedding_provider_integration()`:

1. **Product defect, same shape as T-IGX-036-X.** The catalog holds one `openai` row with categories `[managed_retrieval, embedding_provider]`; its factory is `create_openai_managed_retrieval` (owner `managed_retrieval/openai`). `embedding_provider/openai/register.py` only calls `augment_integration_contract_specs("openai", ...)` and leaves the owning factory in charge of both categories. `resolve(EMBEDDING_PROVIDER, "openai")` raises `IntegrationConfigurationError` ("requires OPENAI_API_KEY or explicit api_key") without a key, and `TypeError ... returned OpenAIManagedRetrievalIntegration, expected EmbeddingProviderIntegrationContract` once a key is present. `resolve` passes `integration_category=` to the factory of every multi-category row, so a wrapper that dispatches on it is the whole fix.
2. **Looked for a second layer and found none.** A throwaway prototype of the ollama-shaped wrapper (not committed) gives: embedding category resolves to `OpenaiEmbeddingProviderIntegration` with and without a key, `config={"enabled": True}` reaches the integration, managed retrieval is unchanged (still needs the key and returns `OpenAIManagedRetrievalIntegration`), still one `openai` row, and `compute_catalog_state_digest` is identical before and after the wrap (the digest excludes factories). The ebh_5 dual-slug harness catalog covers embedding only for `ollama` and `hf` (`_package_c_v2_dual_slug_catalog.py`), so no harness precondition like T-IGX-036-X layer 1 is needed. The compat_x plugin/provider r4 inventory classifies any `register_integration` call in `integrations/providers/**/register.py` as a catalog delegate without per-path pins (code read), so a new call in the openai register module needs no inventory edit (to be verified by running the gate in Deliverable 6, step A).
3. **Survey of the other shared-slug rows.** Full bootstrap (`register_default_integrations(preset="full")`) yields 199 slugs and exactly two rows with more than one category: `ollama` (already fixed, T-IGX-036-X) and `openai`. `hf`, `vllm` and `llama_cpp` are single-category rows owned by their embedding providers (`register_from_manifest`, factories `create_hf_/create_vllm_/create_llama_cpp_embedding_provider`, no other provider shares those slugs): no defect, no change. `augment_integration_contract_specs` has exactly two production callers, `embedding_provider/ollama/register.py` and `embedding_provider/openai/register.py`. Fix scope is therefore the `openai` row only.
4. **F-50 (ollama wrapper pins) is a test gap, not a runtime defect.** Repeated embedding registration does not nest the ollama wrapper: a second call raises `ValueError: ... contract spec category 'embedding_provider' is already registered` (augment refuses a duplicate category), and a second full bootstrap with `override=True` leaves the `ollama` factory at wrapper depth 1 with an unchanged digest. The auditor's surviving mutants (M4 `enabled` hard-wired True, M5 default True, M6 `enabled` ignored, M9 owning factory called without keyword arguments) are not pinned by the existing tests; they are pinned here, test-only.

### Repair 2 — F-41: no ENT-AUDIT impact rule for the Tier-3 `applications/` root

1. **Reproduced (simulation).** `intergrax/platform/enterprise_audit/impact_map.py` (`PDC_DOMAIN_IMPACT_RULES`, merged by `build_impact_map_from_manifest`) and its generated SSOT `intergrax/platform/enterprise_audit/data/changed_since_impact_map.v1.json` (114 prefixes, none starting with `applications`) have no rule for the root `applications/`. Running the logic of the two failing tests (`tests/qualification/pdc_x/xd/test_xd_12_evol_ent_audit.py::test_xd12_every_pdc_touched_product_module_maps_to_a_domain_check` and `tests/qualification/pdc_x/p6_impact/test_p6_impact_map_coverage.py::test_every_pdc_touched_product_module_maps_to_at_least_one_check`) over `development` alone gives no unmapped module (both tests are green there: 53 passed, with `test_changed_since_impact_map.py`), and over the `development` PDC range plus the `.py` paths of `git diff origin/development...origin/mcp-rc` gives exactly the 8 modules `applications/{dispute_sim,governed_contractor,intergrax_assistant,lab,legal,local_workspace,poc_template,research}_application/mcp/server.py`. All other `.py` paths of the MCP-RC delta in product roots already map (`intergrax/applications`, `intergrax/contracts`, `intergrax/tools` rules). **Inferred, not run:** the two real tests on a merged `development` + `mcp-rc` tree (no such tree was built in the planning session; the implementer builds a throwaway one, see Acceptance).
2. **Hidden second layer, reproduced.** The obvious fix, a row `("applications", ids)` in `PDC_DOMAIN_IMPACT_RULES`, makes the existing `test_pdc_domain_rule_prefixes_are_unique_normalized_product_prefixes` fail (it asserts `prefix.startswith("intergrax/")`). That test may not be narrowed (handoff acceptance), so the Tier-3 root rule cannot live in the existing table. It goes into a second typed table with its own pinned tests.
3. **Rule content.** Longest-prefix-wins matching (`check_ids_for_changed_path`) makes a root `applications` prefix match only paths under `applications/`; it does not shadow `intergrax/applications`. Candidate ids come from the existing `intergrax/applications` rule, whose eight ids already fit application-layer code: `ENT-A-BND-01`, `ENT-A-CTR-01`, `ENT-A-CTR-02`, `ENT-A-CTR-03`, `ENT-A-TYP-01`, `ENT-A-SEC-01`, `ENT-A-SEC-02`, `VBN-CONTRACT-LEAKAGE` (all exist in the 85-check manifest; no id is invented). Side effect to record: any changed file under `applications/` (not only `mcp/server.py`) now selects these eight checks in CHANGED-SINCE runs instead of the invariant floor only; that strengthens selection and drops nothing.
