## Problem

The base is `origin/development` at `b86290c95` (PR 538 merge), product tree `146e7acf1` (EBH-7 pin).

1. **R-05: the `pdc_x` pytest process does not exit after its summary line.** Reproduced once, whole suite, time-limited: `930 passed, 6 skipped in 428.68 s`, after which a diagnostic wrapper listed the threads still alive: exactly one, `dependency-admission-boundary`, `daemon=False`, target `DependencyAttemptExecutionBoundary._run_admission_loop` (`intergrax/runtime/resilience/dependency_attempt_execution_boundary.py:285-288`). `threading._shutdown` joins non-daemon threads at interpreter exit, so the process idles until it is killed. The same wrapper on one file, `tests/qualification/pdc_x/xd/test_xd_03_agent_governance.py`, gave `9 passed` and the same single leaked thread, so the leak is in that file. The cause: `test_xd03_strict_composition_refuses_to_build_without_governance` (line 244) calls `materialize_tool_dependency_attempt_boundary(...)`, which starts the admission thread, and then expects `build_production_runtime_tool_invoker(...)` to raise before any invoker owns the boundary; nothing ever calls `boundary.close()`. The seven other tests of the file call `invoker.close()`, but only after the call under test, so an exception there would leak the same way. The thread is by design non-daemon in the product (the boundary must be closed by its owner); this is a test-side leak, not a product defect. Why Run 3 of the acceptance record exited normally: it did not instantiate a boundary.
2. **Tests that are red on the baseline for environment or stale-fixture reasons.** One bounded run over the named test ids of the T reports and the acceptance record (`11 failed, 16 passed in 131.87 s`) split the reds into two groups.

## Deliverables (tests first)

1. **Leak guard and its tests (item 1).** New `tests/qualification/pdc_x/conftest.py` with a module-scoped autouse fixture that records the live non-daemon threads before a module and, at module teardown, fails the module (error at teardown) if a non-daemon thread started during the module is still alive after a short grace wait (at most 2 s of polling); the failure message names the thread and its target. New `tests/qualification/pdc_x/p6_debt/test_p6debt_thread_exit.py`:
   - (a) the guard helper detects a deliberately leaked non-daemon thread (blocked on an `Event`, released in `finally`) and ignores daemon threads and threads that finished;
   - (b) the exit proof: a subprocess `sys.executable -m pytest tests/qualification/pdc_x/xd/test_xd_03_agent_governance.py -q` with `timeout=120` must return exit code 0 within the limit (on the unchanged tree it hangs and `subprocess.run` raises `TimeoutExpired`; the limit is more than ten times the 8 s the file needs).
   Both fail or hang on the unchanged tree for the reason in Problem 1.
2. **Test-side fix of the leak.** In `xd/test_xd_03_agent_governance.py` the refusal test closes the materialized boundary in `finally`, and the `_invoker` helper registers every invoker it builds on a module list closed by an autouse fixture, so a failing assertion cannot leave a thread behind. No assertion changes meaning; no product file changes.
3. **Stale and environment reds (item 2).** Each fix is in the test file only and keeps every assertion:

   Each of the four modules is run before the edit (red) and after (green) in the same pytest invocation as the new tests.
4. **Remove the unused manifest (item 3).** Delete `intergrax/integrations/providers/embedding_provider/ollama/manifest.py` (remove, not wire: wiring it into the catalog would create a second `ollama` row and break the single-row rule fixed by T-IGX-036-X: one `ollama` row owned by `model_serving_runtime/ollama`).
